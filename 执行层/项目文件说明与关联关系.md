# Spec-Kit Pipeline 项目文件说明与关联关系

> 本文基于当前仓库实际文件结构与代码实现整理，说明各目录、文件、执行链路及相互关系。

## 1. 项目定位

本仓库 `spec-kit-pipeline` 是围绕 Spec Kit 平台建设的**测试治理与质量门禁编排项目**。它主要使用 Python 标准库实现，不直接承载被测业务系统，也不直接存放正式 Playwright 测试，而是与相邻目录 `../spec-kit-autotest` 中的 Playwright 自动化测试项目协同工作。

项目包含两条主要链路：

1. **质量门禁主链路**：编排契约检查、静态扫描、缺陷模式回归、Playwright 回归和变异测试，统一输出报告。
2. **离线测试资产生产链路**：从契约、HAR 和已有测试源码中发现测试资产，生成待审核候选用例；经人工审核后，向隔离目录生成 Playwright 脚本预览。

核心原则是：

> AI 可以辅助发现资产、生成用例和脚本，但不能自行审批，也不能替代自动化执行工具与人工业务审核。

### 1.1 现网平台代理视图

浏览器只读扫描产生的现网模块代理视图存放在：

- `spec-kit-pipeline/artifacts/discovery/live-platform-20260824/platform-structure.json`：机器可读的平台模块、能力、数量、风险和未执行动作；
- `spec-kit-pipeline/artifacts/discovery/live-platform-20260824/platform-structure.md`：人可读的结构树与新增发现。

该视图只描述浏览器实际观察到的页面和能力入口，不把 UI 路由臆测为 API 契约，也不保存登录凭据、用户明细、对话全文或模型密钥。

## 3. 顶层目录与文件

| 路径 | 用途 | 关联关系 |
|---|---|---|
| `README.md` | 项目总说明，包括理念、运行方式、门禁说明和目录结构。 | 指向 `pipeline.py`、`config.json`、`gates/`、`assets/`、`tools/` 与 `report/`。 |
| `pipeline.py` | **主入口**：读取配置、执行 Gate、处理状态与退出码、生成报告。 | 从 `gates/__init__.py` 获取全部门禁；读取 `config.json`；可调用 `tools/fetch_contract.py`。 |
| `config.json` | 全局运行配置：环境、被测目标、外部 Playwright 项目路径、各 Gate 策略等。 | 被 `pipeline.py` 和全部 Gate 使用。 |
| `gates/` | 质量门禁模块。 | 由 `pipeline.py` 统一编排。 |
| `tools/` | 契约拉取、资产发现、候选用例生成、隔离脚本生成工具。 | 共享 `tools/common.py` 的安全与校验能力。 |
| `assets/` | 人工维护的缺陷模式库、AI 黄金集、关键契约兜底数据。 | 分别被模式回归、契约回退和 AI 质量评估使用。 |
| `schemas/` | 三类中间产物的 JSON Schema。 | 对应 `discover`、`generate_cases`、`generate_playwright` 的输出。 |
| `artifacts/` | 历史测试资产发现结果、候选用例结果。 | 是工具链中间产物和审计证据。 |
| `.pipeline-cache/` | 临时缓存、隔离脚本生成预览和试运行产物。 | 不应视为正式测试代码目录。 |
| `tests/` | 本项目 Python 工具、状态模型和测试治理逻辑的单元测试。 | 使用 `unittest`，并包含测试 fixture。 |
| `report/` | 每次流水线运行的 JSON/Markdown 报告，以及管理类文档。 | 由 `pipeline.py` 写入。 |

`__pycache__/` 为 Python 字节码缓存，`.DS_Store` 为 macOS Finder 元数据，均不属于项目实现。

## 4. 主入口：`pipeline.py`

[`pipeline.py`](../spec-kit-pipeline/pipeline.py) 是质量门禁流水线的编排入口。

### 4.1 主要职责

- 加载并规范化 `config.json`；
- 按全部、指定 Gate 或指定阶段选择执行范围；
- 初始化并执行各 Gate；
- 将异常转换为统一状态；
- 处理阻断逻辑和退出码；
- 输出 JSON 与 Markdown 执行报告；
- 在指定时委托 `tools/fetch_contract.py` 拉取 OpenAPI 契约。

### 4.2 关键函数

| 函数 | 作用 |
|---|---|
| `load_config()` | 读取配置并解析项目、Playwright、报告目录的绝对路径，同时避免路径越界。 |
| `run_gate()` | 初始化 Gate、执行 Gate，并将配置错误、环境错误、阻断错误映射为统一状态。 |
| `write_report()` | 生成 `report/pipeline-*.json` 和 `report/pipeline-*.md`。 |
| `fetch_contract()` | 通过子进程调用 `tools/fetch_contract.py`。 |
| `main()` | 解析 CLI 参数、筛选 Gate、控制执行顺序、返回退出码。 |

### 4.3 支持的常用命令

```bash
# 执行全部启用的门禁
/opt/homebrew/bin/python3 pipeline.py

# 仅做初始化校验，不实际运行门禁
/opt/homebrew/bin/python3 pipeline.py --dry-run

# 按阶段执行
/opt/homebrew/bin/python3 pipeline.py --stage code
/opt/homebrew/bin/python3 pipeline.py --stage smoke
/opt/homebrew/bin/python3 pipeline.py --stage test
/opt/homebrew/bin/python3 pipeline.py --stage release

# 只执行一个门禁
/opt/homebrew/bin/python3 pipeline.py --gate static_scan

# 拉取当前 OpenAPI 契约
/opt/homebrew/bin/python3 pipeline.py --fetch-contract --auto-login
```

### 4.4 状态和退出码

| 状态 | 含义 |
|---|---|
| `PASS` | 门禁通过。 |
| `FAIL` | 普通失败。 |
| `BLOCKED` | 阻断性门禁失败，后续门禁不再执行。 |
| `SKIP` | 门禁未执行，必须与通过严格区分。 |
| `FLAKY` | 用例存在波动。 |
| `ENV_ERROR` | 测试环境异常、不可达或不稳定。 |
| `CONFIG_ERROR` | 配置错误，或必需 Gate 被禁用/跳过。 |

| 退出码 | 含义 |
|---:|---|
| `0` | 全部通过，或全部 Gate 均跳过。 |
| `1` | 存在普通失败或波动。 |
| `2` | 配置错误或必需门禁不可用。 |
| `3` | 阻断性门禁失败。 |
| `4` | 环境异常。 |

## 5. 配置中心：`config.json`

[`config.json`](../spec-kit-pipeline/config.json) 集中定义运行环境和各 Gate 策略。

### 5.1 全局配置

```json
{
  "environment": "production-like",
  "project_root": ".",
  "autotest_dir": "../spec-kit-autotest",
  "target": {
    "base_url": "https://106.54.60.191",
    "openapi_path": "/api/v1/openapi.json"
  }
}
```

含义：

- `environment`：默认环境类型；
- `project_root`：当前流水线项目目录；
- `autotest_dir`：相邻的实际 Playwright 自动化项目；
- `target.base_url`：Spec Kit 被测平台地址；
- `target.openapi_path`：预期 OpenAPI 文档地址。

### 5.2 Gate 通用配置项

每个 `gates.<gate_name>` 可配置：

| 字段 | 含义 |
|---|---|
| `enabled` | 是否启用 Gate。 |
| `required` | 是否为必需 Gate。 |
| `skip_policy` | 跳过时采取 `allow`、`warn` 或 `fail`。 |
| `stages` | 在哪些流水线阶段运行。 |

`e2e_regression` 还基于阶段映射不同 npm script：

```json
"scripts_by_stage": {
  "code": "test:unit",
  "smoke": "test:api:readonly",
  "test": "test:ci",
  "release": "test:ci",
  "ai": "test:api:ai",
  "destructive": "test:api:destructive"
}
```

## 6. 门禁模块：`gates/`

```text
gates/
├── __init__.py
├── base.py
├── contract_diff.py
├── static_scan.py
├── pattern_regression.py
├── e2e_regression.py
└── mutation_check.py
```

### 6.1 `gates/__init__.py`：门禁注册表

`ALL_GATES` 定义流水线 Gate 注册与默认执行顺序：

1. `ContractDiffGate`
2. `StaticScanGate`
3. `PatternRegressionGate`
4. `E2ERegressionGate`
5. `MutationCheckGate`

新增 Gate 时，需要新建模块、继承 `Gate`、在此文件中注册，并在 `config.json` 中补充配置。

### 6.2 `gates/base.py`：统一 Gate 接口

该文件定义：

- `GateStatus`：所有状态枚举；
- `GateResult`：Gate 返回结果，包含状态、详情、问题列表和指标；
- `Gate`：抽象父类；
- `GateSetupError`：配置或依赖缺失；
- `GateEnvironmentError`：目标环境异常；
- `redact_sensitive()`：报告文本的凭据脱敏。

具体 Gate 都遵循：

```python
def init(self) -> None:
    ...

def run(self) -> GateResult:
    ...
```

---

### 6.3 `gates/contract_diff.py`：OpenAPI 契约差异门禁

该 Gate 是**阻断性门禁**，用于比较基线和当前 OpenAPI 契约：

```text
assets/contract/snapshot.json  ← 已批准的基线
assets/contract/current.json   ← 当前拉取版本
```

主要检测：

- 接口端点新增或删除；
- 必填字段新增或移除；
- 枚举值新增或移除；
- OpenAPI 版本变化。

以下变更会阻断流水线：

```text
removed_endpoint
removed_required_field
removed_enum_value
```

当无法获取当前 OpenAPI 时，Gate 读取 [`assets/contract/key-contracts.json`](../spec-kit-pipeline/assets/contract/key-contracts.json) 中人工维护的关键接口，并扫描 `../spec-kit-autotest/tests/api/**/*.js`，检查这些接口是否已有自动化覆盖。

因此其关系为：

```text
OpenAPI 可用
  → snapshot.json 与 current.json 做差异比较

OpenAPI 不可用
  → key-contracts.json 检查关键接口自动化覆盖
```

---

### 6.4 `gates/static_scan.py`：静态扫描门禁

静态扫描 Gate 用于识别敏感信息泄露和不安全编码痕迹。

内置规则包括：

- 硬编码 AccessKey；
- 硬编码 SecretKey；
- 硬编码 API Key；
- 硬编码 Token；
- 疑似硬编码密码；
- 在日志中输出密码、Token、Secret 或 Key。

除内置正则外，还能调用外部工具。例如当前配置支持：

```text
code 阶段：npm run lint
release 阶段：npm run lint + Semgrep
```

工作关系：

```text
外部 Playwright 项目源码
      ↓
内置正则扫描 + lint / Semgrep 等外部工具
      ↓
统一生成 GateResult
```

---

### 6.5 `gates/pattern_regression.py`：AI 缺陷模式回归门禁

该 Gate 是**阻断性门禁**，读取 [`assets/patterns.json`](../spec-kit-pipeline/assets/patterns.json)，对 AI 高发缺陷模式进行基础回归。

目前模式库包含十类问题：

1. 空值 / 空指针；
2. 并发 / 竞态；
3. 边界值；
4. 鉴权 / 越权；
5. 时区 / 时间；
6. 编码 / 国际化；
7. 正则 / 输入校验；
8. 资源 / 连接；
9. 事务 / 一致性；
10. 幂等性。

支持两种探测：

| 探测方式 | 用途 |
|---|---|
| `probe` | 对目标平台发起只读 HTTP 探测，检查状态码或响应特征。 |
| `file_check` | 检查流水线项目或 Playwright 项目的目标文件是否存在。 |

该 Gate 只做低风险、只读体检。注入、越权、写操作、并发压测等高风险场景仍应在隔离环境下，经人工授权后执行。

---

### 6.6 `gates/e2e_regression.py`：Playwright 回归门禁

这是本项目与正式 Playwright 自动化项目之间的主要连接点。

执行关系：

```text
pipeline.py
  ↓
E2ERegressionGate
  ↓
进入 ../spec-kit-autotest
  ↓
执行 npm run <script>
  ↓
读取 reports/test-results.json
  ↓
计算通过率、失败数、波动数
  ↓
返回 GateResult
```

关键控制：

- 依据运行阶段选择 npm script；
- 执行前删除旧 `reports/test-results.json`，避免读取历史报告造成“假绿”；
- 优先解析 Playwright JSON Reporter 的 `stats`；
- 依据最小通过率阈值（当前为 `0.95`）判定；
- 能识别 `FLAKY`；
- 可将多次环境异常归类为 `ENV_ERROR`。

它反映的是“自动化回归是否通过”，不能替代人工对业务正确性、核心断言和高风险场景的审核。

---

### 6.7 `gates/mutation_check.py`：变异测试门禁

该 Gate 用于验证自动化测试断言是否真正能发现缺陷，防止“代码和测试都由同一来源生成而导致的同源假绿”。

当前配置已指定：

```text
npm run test:mutation
```

理论流程：

```text
注入变异体（人为缺陷）
  ↓
执行现有测试
  ↓
统计被测试捕获的变异体比例（kill rate）
  ↓
与 min_kill_rate = 0.7 比较
```

当前该 Gate 已实际接入 Stryker，而不再是纯占位。不过当前实现的解析逻辑主要识别类似 `xx.xx% killed` 的格式；若 Stryker 只输出 `Final mutation score 54.60`，可能无法提取数值，从而出现解析适配问题。

## 7. 测试资产与治理数据：`assets/`

```text
assets/
├── patterns.json
├── golden_set.json
└── contract/
    └── key-contracts.json
```

### 7.1 `assets/patterns.json`

AI 高发缺陷模式库，也是 `pattern_regression` 的直接输入。

每条模式通常包含：

- 模式编号；
- 缺陷类别；
- 常见错误；
- Spec Kit 平台风险点；
- 只读探测配置；
- 关联标准测试用例；
- 执行边界说明。

它应随测试实践持续回填：

```text
新发现的集中缺陷
  ↓
补充模式库
  ↓
后续每轮迭代自动执行基础回归
```

### 7.2 `assets/golden_set.json`

AI 质量评估黄金集登记文件。它不是 Playwright 测试数据，而是评估 AI 在需求、SDD、Judge 等阶段产出质量的样本基线。

其中可记录：

- 需求等级；
- SDD 阶段；
- 输入类型；
- 双专家独立标注；
- 仲裁结果；
- 人与人一致性；
- 人与机器一致性；
- 模型、提示词、规则版本等元数据。

### 7.3 `assets/contract/key-contracts.json`

人工审核的关键接口清单。在 OpenAPI 无法拉取时，由 `ContractDiffGate` 作为兜底数据源。

当前登记的关键领域包括：

- 登录；
- 会话；
- 需求；
- SDD；
- 任务；
- 质量门禁。

## 8. 工具链：`tools/`

```text
tools/
├── common.py
├── fetch_contract.py
├── discover.py
├── generate_cases.py
└── generate_playwright.py
```

该工具链体现“构建 AI 可调用测试环境”的方向，但严格区分发现、生成、审批和正式执行。

### 8.1 `tools/common.py`：共享安全与校验能力

多个工具共同依赖该文件。

| 能力 | 关键函数 |
|---|---|
| 内容摘要 | `digest()`、`file_digest()` |
| 敏感信息脱敏 | `redact()` |
| 路径边界控制 | `resolve_path()`、`assert_within()`、`assert_isolated_output()` |
| 原子写文件 | `atomic_write()`、`write_json()` |
| 资产文档校验 | `validate_asset_doc()` |
| 候选用例校验 | `validate_candidate_doc()` |
| 生成清单校验 | `validate_generation_manifest()` |

关键安全约束：

- 产物不能写到正式测试目录或其他受保护目录；
- 输出必须处于受控工作区；
- 密码、Token、Cookie、密钥等必须脱敏；
- 自动化候选必须经过人工批准；
- 破坏性测试不能在 `production-like` 环境运行；
- 写操作必须声明清理策略。

依赖关系：

```text
discover.py ──────────────┐
generate_cases.py ────────┼──> common.py
generate_playwright.py ───┤
fetch_contract.py ────────┘
```

### 8.2 `tools/fetch_contract.py`：OpenAPI 契约拉取

该工具可独立运行，也可被 `pipeline.py --fetch-contract` 调用。

```bash
python3 tools/fetch_contract.py --auto-login --save-baseline
python3 tools/fetch_contract.py --token <token>
python3 tools/fetch_contract.py --path /v3/api-docs
```

执行关系：

```text
config.json
  ↓ 获取 base_url / openapi_path / autotest_dir
读取 ../spec-kit-autotest/.env 或 SPEC_KIT_TOKEN
  ↓
可选：调用登录接口获取 accessToken
  ↓
拉取并校验 OpenAPI JSON
  ↓
保存 assets/contract/current.json
  ↓
可选：保存 assets/contract/snapshot.json
```

安全控制：

- 默认开启 TLS 证书验证；
- 只有显式使用 `--insecure` 才关闭验证；
- `production-like` 环境禁止 `--insecure`；
- 不打印账号、密码或 Token；
- 覆盖基线必须显式使用 `--force-baseline`。

### 8.3 `tools/discover.py`：离线测试资产发现

该工具不会直接执行测试，而是从不同来源构建“可测试资产清单”。

支持的输入：

| 输入 | 发现内容 |
|---|---|
| OpenAPI / 契约 JSON | 接口、方法、参数、响应码、请求结构、鉴权信息。 |
| HAR 文件 | 真实观察到的请求流、响应状态、响应结构。 |
| Playwright 源码和配置 | API 调用点、已有测试标题、已有覆盖路径。 |
| 本地测试文件 | 已有测试资产与证据引用。 |

示例：

```bash
python3 tools/discover.py \
  --root .. \
  --pipeline-root . \
  --autotest-root ../spec-kit-autotest \
  --contract assets/contract/key-contracts.json \
  --out-dir artifacts/discovery/check3 \
  --validate
```

输出：

```text
artifacts/discovery/<run-id>/
├── discovered-assets.json
└── discovered-assets.md
```

主要字段：

- `assets.endpoints`：已发现接口；
- `assets.observed_flows`：HAR 观察到的调用流；
- `assets.source_rules`：源码 API 调用证据；
- `assets.tests`：已有 Playwright 测试；
- `evidence`：资产来源、位置、哈希、脱敏状态；
- `conflicts`：发现过程中的冲突；
- `summary`：统计信息。

关系：

```text
discover.py
  ↓
discovered-assets.json
  ↓
generate_cases.py
```

### 8.4 `tools/generate_cases.py`：候选测试用例生成

该工具以 `discovered-assets.json` 为输入，确定性生成候选测试用例，而不是直接生成可执行脚本。

典型候选场景包括：

- 请求可达性；
- 响应结构；
- 缺少必填字段；
- 字段边界；
- 未认证访问。

输出：

```text
artifacts/candidates/<run-id>/
├── candidate-cases.json
└── candidate-cases.md
```

设计约束：

- 默认状态为 `CANDIDATE` 或 `BLOCKED`；
- 默认 `automatable: false`；
- 默认所有断言需要人工确认；
- 已存在覆盖时默认不重复生成；
- 破坏性接口默认阻断；
- 写操作仅允许在隔离环境中考虑自动化；
- 每个产物都有 `input_digest`，便于追溯来源。

关系：

```text
discovered-assets.json
      ↓
generate_cases.py
      ↓
candidate-cases.json
      ↓
人工审核、补全业务断言、批准
      ↓
generate_playwright.py
```

### 8.5 `tools/generate_playwright.py`：隔离 Playwright 脚本预览生成

该工具只对已经人工审核并批准的候选用例生成 Playwright 脚本骨架。

候选必须满足：

```text
lifecycle_status == "AUTOMATABLE"
review.decision == "approve"
automatable == true
存在 evidence_refs
不存在仍需人工确认的断言
```

同时：

- 默认只允许只读用例；
- 即使传入写操作授权，当前模板仍拒绝 stateful / destructive 用例；
- 原因是资源登记与自动清理模板尚未完整实现；
- 不允许直接写入正式 Playwright `tests/` 目录；
- 仅可写入隔离目录；
- 会扫描生成内容中的潜在敏感信息。

输出：

```text
<out-dir>/
├── tests/
│   └── generated_<case-id>.spec.js
├── evidence/
│   └── <case-id>.json
├── manifest.json
└── README.md
```

`manifest.json` 记录：

- 输入候选用例摘要；
- 生成 case ID；
- 文件路径；
- 模板版本；
- 受保护目录；
- Schema、路径边界、敏感信息扫描状态；
- lint、Playwright 发现与实际执行状态。

定位：

> AI 或规则可以生成隔离预览脚本；只有人工审查确认后，才能决定是否迁入正式 Playwright 项目。

```text
schemas/
```

| Schema | 对应产物 | 生产者 |

## 10. 测试目录：`tests/`

```text
tests/
├── test_governance.py
├── test_pipeline_trust.py
├── test_tools.py
└── fixtures/
    └── approved-candidates.json
```

这些是**本仓库 Python 工具与治理规则**的单元测试，不是 Spec Kit 平台的业务测试。

### 10.1 `tests/test_governance.py`

验证治理基础能力：

- Gate 状态归一化；
- 必需 Gate 初始化失败转为 `CONFIG_ERROR`；
- 可选 Gate 初始化失败转为 `SKIP`；
- `skip_policy` 是否正确执行；
- 环境异常是否映射为退出码 4；
- 删除接口是否识别为破坏性契约变化；
- 路径是否被解析为绝对路径；
- 报告是否脱敏；
- 报告文件名是否避免冲突。

### 10.2 `tests/test_pipeline_trust.py`

验证“执行结果可信性”和“防假绿”能力：

- `SKIP` 是否与 `PASS` 严格区分；
- 汇总报告是否不将跳过计入通过；
- 阻断性 Gate 异常是否保持阻断语义；
- 旧 Playwright JSON 报告是否会在执行前删除；
- 是否只解析本轮生成的新报告。

### 10.3 `tests/test_tools.py`

验证离线工具链的安全和生成规则：

- 人工契约是否能解析正确 HTTP 方法；
- HAR 查询参数是否始终脱敏；
- 候选用例是否不能自批准；
- 候选是否必须具备断言；
- 未审核候选是否不能生成 Playwright；
- 已审核只读候选是否生成真实 `expect(...)` 断言；
- 有状态用例在清理模板未实现前是否被拒绝；
- TLS 是否默认验证；
- 契约基线是否拒绝隐式覆盖；
- `secret_scan` 状态字段是否能避免被误脱敏。

### 10.4 `tests/fixtures/approved-candidates.json`

该 fixture 用于模拟一个已审核、已批准、可生成的只读候选用例。它不是生产配置或正式测试资产，而是 `test_tools.py` 的输入样本。

## 11. 历史产物：`artifacts/`

```text
artifacts/
├── discovery/
│   └── check2/
│       ├── discovered-assets.json
│       └── discovered-assets.md
└── candidates/
    └── check2/
        ├── candidate-cases.json
        └── candidate-cases.md
```

### 11.1 `artifacts/discovery/check2/`

`discovered-assets.json` 记录了一次实际测试资产发现结果，包含：

- 核心接口；
- `spec-kit-autotest` 中已有 API、UI、单元测试；
- 测试标题、源码哈希、调用位置；
- 契约与源码证据；
- 初步覆盖判断。

`discovered-assets.md` 是其人工可读版本。

### 11.2 `artifacts/candidates/check2/`

`candidate-cases.json` 是从发现资产生成的历史候选用例；记录测试类型、风险、操作步骤、预期、证据、覆盖情况和审批状态。

`candidate-cases.md` 是便于人工评审的 Markdown 版本。

### 11.3 当前版本注意事项

当前 `check2` 产物存在版本漂移迹象：其中使用 `candidate_id`、`DRAFT` 等历史字段，而当前工具与 Schema 已转向 `case_id` 和更严格的统一生命周期状态。

因此建议：

```text
check2：保留为历史实测与审计证据
check3：使用当前工具重新生成的新产物目录
```

不要覆盖 `check2`，以便后续比较规则变更前后的结果。

### 12.1 `pipeline-*.json` 和 `pipeline-*.md`

### 13.2 AI 辅助测试资产生产链路

```text
OpenAPI / key-contracts.json / HAR / Playwright 源码
   ↓
tools/discover.py
   ↓
artifacts/discovery/<run-id>/discovered-assets.json
   ↓
tools/generate_cases.py
   ↓
artifacts/candidates/<run-id>/candidate-cases.json

   ↓
```

## 14. AI、Harness、人工与 Playwright 的职责边界

| 角色 / 组件 | 主要职责 | 不应承担的职责 |
|---|---|---|
| AI / 生成工具 | 辅助发现资产、生成候选用例、生成隔离脚本骨架、整理测试文档。 | 自行审批、直接写入正式测试目录、替代业务判断。 |
| `tools/` | 离线扫描、格式校验、风险限制、候选与隔离脚本生成。 | 直接替代正式测试执行和人工验收。 |
| Harness / `pipeline.py` | 编排 Gate、调用外部测试、收集结果、统一报告。 | 判断复杂业务逻辑是否符合真实业务预期。 |
| Playwright 项目 | 执行 API、UI、回归测试并输出执行结果。 | 替代契约治理、审批治理和风险判断。 |
| 人工测试人员 / 审批人 | 编写核心断言、审核候选、确认风险边界、批准脚本、判定业务结果。 | 将所有重复性执行完全手工化。 |
| Gate 门禁 | 对规则化风险进行检查与阻断。 | 用单一“通过”掩盖跳过、环境异常或待人工确认事项。 |

## 15. 推荐阅读顺序

1. `README.md`：理解项目目标、原则和运行方式；
2. `config.json`：了解环境、阶段和 Gate 配置；
3. `pipeline.py`：理解总调度流程；
4. `gates/base.py`：理解统一状态和 Gate 接口；
5. `gates/__init__.py`：查看门禁注册与执行顺序；
6. 依次阅读五个具体 Gate；
7. `tools/common.py`：理解工具链安全边界；
8. `discover.py → generate_cases.py → generate_playwright.py`：理解资产发现和 AI 辅助生成链路；
9. `schemas/`：理解中间产物结构；
10. `tests/`：了解当前重点验证的治理风险；
11. `artifacts/` 与 `report/`：查看历史实测证据与执行结果。
