# 自然语言下的测试用例转自动化操作

> 目标：将自然语言测试用例转换为可重复执行、可审查、可接入流水线门禁的 Playwright 自动化测试。
>
> 本文适用于工作区中的两个项目：
>
> - `spec-kit-autotest`：测试执行层，保存 Playwright API/UI 用例、测试工具和原始报告。
> - `spec-kit-pipeline`：测试治理层，调度自动化、执行门禁并生成准入报告。

---

## 1. 核心原则：不能把自然语言直接“翻译”为代码

自然语言测试用例往往是泛化描述，例如：

> 进入需求管理，填写测试数据，提交需求，核对页面反馈和接口响应。

这只说明“要测什么”，没有明确：

- 使用哪个账号、角色和环境；
- 调用哪个接口或操作哪个页面元素；
- 请求数据是什么；
- 成功或失败的精确判定条件；
- 写入数据后怎样清理；
- 哪些验证可在现网执行，哪些只能在隔离环境执行。

如果直接让 AI 根据这类描述生成代码，AI 会补全未提供的信息，产生“猜出来但能跑”的测试。这会造成测试通过却没有真正验证业务规则的 **假绿**。

因此，应遵循：

```text
自然语言用例
→ 人工去泛化，补齐可执行规格
→ 映射为 API/UI 自动化操作
→ AI 可辅助生成代码骨架
→ 人工复核关键断言
→ 单独实跑并验证清理
→ 接入 pipeline 回归门禁
```

关键断言——尤其是状态流转、权限、审批、安全、幂等性等——必须由人工进行背靠背审查，不能由生成业务代码的同一模型直接决定后自动入库。

---

## 2. 第一步：判断用例是否适合自动化

先从自然语言用例中提取以下信息。

| 信息 | 需要明确的内容 |
|---|---|
| 用例标识 | TC ID、模块、优先级（如 P0/T0） |
| 前置条件 | 登录状态、用户角色、已有数据、环境类型 |
| 操作类型 | API、UI、文件上传、异步任务、并发、AI 调用等 |
| 测试数据 | 正常值、空值、边界值、非法值、权限账号 |
| 预期结果 | 状态码、响应字段、页面提示、状态迁移、审计记录 |
| 副作用 | 是否创建、修改、删除资源；是否需要回收 |
| 风险等级 | 是否为有状态、AI、破坏性或安全攻击性验证 |

### 2.1 按环境和风险划分

| 用例类型 | `production-like` 环境 | `isolated` 环境 | 必要开关 |
|---|---:|---:|---|
| 只读 API / 无害冒烟 | 可执行 | 可执行 | 无 |
| 创建、审批、归档等有状态操作 | 不可执行 | 可执行 | `ALLOW_STATEFUL_TESTS=true` |
| AI 真实调用 | 默认不执行 | 可执行 | `RUN_AI_TESTS=true` |
| 删除、破坏性、安全攻击性验证 | 不可执行 | 可执行 | `TEST_ENV_TYPE=isolated` + `ALLOW_DESTRUCTIVE_TESTS=true` |

现网或类生产环境只能运行只读、低风险、无害验证。越权、注入、删除、并发写入和真实 AI 长任务，应在隔离环境执行。

---

## 3. 第二步：去泛化——把自然语言变成可执行规格

这是最重要的一步，应由了解业务和验收规则的人主导。

### 3.1 转换模板

将每条自然语言用例整理为以下格式：

```text
用例 ID：TC-XXX-001
名称：<业务功能>-<验证点>
优先级：P0 / P1 / P2
类型：API / UI / 安全 / AI / 性能
执行环境：production-like / isolated

前置条件：
  1. <账号或角色>
  2. <已有业务数据或前置状态>

测试数据：
  - 正常值：...
  - 异常值：...
  - 边界值：...

操作步骤：
  1. 调用 <HTTP 方法 + API 路径>，或进入 <页面路径>。
  2. 输入/提交 <精确数据>。
  3. 获取或观察 <响应/页面状态/数据库或审计记录>。

预期结果：
  1. HTTP 状态码为 ...。
  2. 响应中字段 ... 满足 ...。
  3. 不应产生 ... 副作用；或状态只能从 ... 流转到 ...。
  4. 页面显示 ...。

清理：
  - 删除本用例创建的资源；或由 resourceTracker 自动清理。
```

### 3.2 示例：从泛化描述到可自动化规格

**原始自然语言：**

> 验证需求标题字段校验，正常、异常和边界值均需验证。

**去泛化后：**

```text
用例 ID：TC-REQ-002
名称：需求管理-标题字段校验
类型：API
执行环境：isolated（该用例会创建资源）

前置条件：member 用户已登录。

测试数据：
  - title = ""（空值）
  - title = 255 个字符
  - title = 256 个字符

操作：
  1. 调用 POST /api/v1/requirements。
  2. 分别使用以上 3 组 title 提交完整需求数据。

预期：
  - 空值：HTTP 400，返回标题必填错误，且无资源创建。
  - 255 字符：创建成功，HTTP 200/201，响应包含新资源 ID。
  - 256 字符：HTTP 400，返回长度校验错误，且无资源创建。

清理：
  - 删除 255 字符场景创建的需求。
```

注意：HTTP 状态码、字段长度和错误码不能凭空猜测，必须从 API 文档、前端校验、后端实现、已有测试或实际探测中确认。

## 4. 第三步：选择 API 自动化还是 UI 自动化

### 4.1 API 自动化优先覆盖业务规则

以下类型优先写在 `spec-kit-autotest/tests/api/`：

- 状态码、响应结构和错误码；
- 鉴权、横向/纵向越权；
- 参数校验、空值、边界值、枚举；
- 状态机流转、审批规则；
- 幂等性、事务一致性；
- 异步任务的状态和结果结构。

API 自动化通常更稳定、更快，更适合精准验证业务规则。

可复用的基础设施：

| 需求 | 项目实现 |
|---|---|
| 已登录 API 调用 | `fixtures/authFixture.js` 中的 `apiClient` |
| 匿名 API 调用 | `fixtures/authFixture.js` 中的 `anonClient` |
| 接口路径 | `env.baseURL + env.api('/xxx')` |
| 唯一测试数据 | `utils/testData.js` |
| 资源回收 | `resourceTracker` |
| 登录能力 | `utils/auth.js` |

### 4.2 UI 自动化验证用户可见的行为

以下类型适合写在 `spec-kit-autotest/tests/ui/`：

- 页面能否打开；
- 表单能否输入、校验提示是否正确；
- 按钮、弹窗、页面跳转；
- 列表显示、筛选、用户可见状态；
- 跨浏览器兼容性。

元素定位优先级：

1. `data-testid`；
2. 语义化 role、label、可见文本；
3. 稳定业务 class；
4. 最后才使用 DOM 层级选择器。

不要使用动态生成的元素 ID（例如 `el-id-*`）作为稳定定位依据。

## 5. 第四步：将可执行规格映射为 Playwright 代码

### 5.1 自然语言与代码的映射

| 自然语言内容 | Playwright 实现 |
|---|---|
| 前置：已登录 | 测试参数中使用 `{ apiClient }` |
| 前置：未登录 | 测试参数中使用 `{ anonClient }` |
| API 操作 | `apiClient.get/post/put/delete(...)` |
| UI 操作 | `page.goto/fill/click/...` 或 `authPage` |
| 统一接口路径 | `env.baseURL + env.api('/xxx')` |
| 唯一测试数据 | `requirementData(...)` 等生成器 + 覆盖字段 |
| 预期结果 | `expect(...)`、状态码断言、结构断言 |
| 创建资源后的回收 | `resourceTracker` 或显式 `delete` |

### 5.2 API 示例：匿名访问必须拒绝

自然语言规格：

> 未登录用户访问需求列表接口，系统应拒绝访问。

可映射为：

```js
const { test, expect, describe } = require('../../fixtures/authFixture');
const env = require('../../config/env');

const API = {
  requirements: () => env.baseURL + env.api('/requirements'),
};

describe('TC-SEC-004 鉴权校验', () => {
  test('未登录访问需求列表返回 401', async ({ anonClient }) => {
    const res = await anonClient.get(API.requirements());
    const body = await res.json();

    expect(res.status()).toBe(401);
    expect(body).toBeTruthy();
  });
});
```

### 5.3 API 示例：写操作要使用唯一数据并清理

写操作用例不能复用固定数据，避免多次执行冲突；同时必须能回收创建的资源。

```js
const { test, expect, describe } = require('../../fixtures/authFixture');
const { requirementData } = require('../../utils/testData');
const env = require('../../config/env');

describe('需求创建', () => {
  test('TC-REQ-001 正常创建需求', async ({ apiClient, resourceTracker }) => {
    const currentUser = await apiClient.get(`${env.baseURL}${env.api('/data/me')}`);
    const currentUserBody = await currentUser.json();

    const data = requirementData({
      reviewerId: currentUserBody.data.id,
    });
    const res = await apiClient.post(`${env.baseURL}${env.api('/requirements')}`, { data });
    const body = await res.json();

    expect(res.status()).toBe(201);
    expect(body.data.id).toBeTruthy();

    resourceTracker.track({
      type: 'requirement',
      id: body.data.id,
      cleanup: async () => apiClient.delete(`${env.baseURL}${env.api(`/requirements/${body.data.id}`)}`),
    });
  });
});
```

实际请求字段、状态码、响应路径和 `resourceTracker` 的具体调用形式，应以项目内同模块的已验证用例为准。

## 6. 第五步：人工审查断言，避免“能跑但没测到”

代码生成后，先不直接入库。应由人工重点审查：

- **状态机**：是否确认了正确的前置状态、禁止跳转和最终状态；
- **权限**：401（未认证）与 403（已认证但无权限）是否区分；
- **越权**：是否真的使用了不同用户、不同团队或不同资源 ID；
- **幂等性**：是否比较重复请求前后的资源数、状态或唯一 ID；
- **失败无副作用**：失败请求是否验证未创建/未修改数据；
- **异步任务**：是否校验最终状态、事件顺序、结果结构和超时处理；
- **AI 输出**：避免精确断言不可预测的文案，优先断言 `ok`、状态、必需字段和结构；
- **环境错误**：不能把 HTML 登录页、503 页面或网关错误误判为成功响应。

可以用“负向验证”检查断言是否真的有效：临时修改一个关键断言或模拟一个错误条件，确认测试会失败。确认后再恢复正确代码。

## 7. 第六步：单文件实跑和结果确认

先在 `spec-kit-autotest` 中单独运行新用例：

```bash
cd /Users/xiaoxu/Desktop/spec-kit/spec-kit-autotest

# API 单文件
npx playwright test tests/api/xxx.spec.js --project=api

# 按测试用例 ID 或标题筛选
npx playwright test tests/api/xxx.spec.js --grep 'TC-REQ-002'

# UI 单文件
npx playwright test tests/ui/xxx.spec.js --project=ui-chromium
```

实跑后确认：

1. 用例确实被发现并执行，而不是被 grep 或 project 配置过滤；
2. 实际执行数与预期一致；
3. 把关键预期改错后，用例能真实失败；
4. 测试数据可以成功清理；
5. 失败时截图、trace、JSON 报告能提供有效诊断信息；
6. 网络错误、HTML 页面和服务端 503 没有被吞掉或误判为成功。

Playwright 的机器可读结果会输出到：

```text
spec-kit-autotest/reports/test-results.json
```

HTML 报告输出到：

```text
spec-kit-autotest/reports/html/
```

## 8. 第七步：登记用例与缺陷模式映射

每个自动化测试标题应保留自然语言用例的 TC ID，例如：

```js
test('TC-REQ-002 需求标题边界校验', async ({ apiClient }) => {
  // ...
});
```

当一批用例转换完成后，更新：

```text
spec-kit-pipeline/assets/patterns.json
```

将其关联到相应缺陷模式，例如：

- 空值/空指针；
- 边界值；
- 鉴权/越权；
- 并发/竞态；
- 编码/国际化；
- 正则/输入校验；
- 事务/一致性；
- 幂等性。

注意：`patterns.json` 中的 `probe` 当前主要用于只读 HTTP 体检，不等价于完整业务自动化。真正的状态流转、边界、权限、并发和幂等性断言，仍须体现在 `tests/api` 或 `tests/ui` 的具体 Playwright 用例中。

## 9. 第八步：接入 pipeline 统一回归

单文件验证通过后，通过 pipeline 统一执行与留痕：

```bash
cd /Users/xiaoxu/Desktop/spec-kit/spec-kit-pipeline

# 代码阶段：静态扫描 + 单元测试
/opt/homebrew/bin/python3 pipeline.py --stage code

# 冒烟阶段：模式回归 + 只读 API
/opt/homebrew/bin/python3 pipeline.py --stage smoke

# 常规回归：模式回归 + lint + unit + 只读 API
/opt/homebrew/bin/python3 pipeline.py --stage test

# 发布前：契约、静态扫描、回归、变异测试
/opt/homebrew/bin/python3 pipeline.py --stage release
```

当前阶段与 autotest 脚本的主要映射如下：

| pipeline 阶段 | autotest 执行脚本 |
|---|---|
| `code` | `npm run test:unit` |
| `smoke` | `npm run test:api:readonly` |
| `test` | `npm run test:ci` |
| `release` | `npm run test:ci` |
| `ai` | `npm run test:api:ai` |
| `destructive` | `npm run test:api:destructive` |

pipeline 会在启动测试前清理 autotest 中旧的 JSON 测试报告，读取本轮 `reports/test-results.json`，再根据测试退出码、通过率、失败数、flaky 状态和环境错误判断最终状态。

最终治理报告输出到：

```text
spec-kit-pipeline/report/pipeline-*.json
spec-kit-pipeline/report/pipeline-*.md
```

## 10. 推荐的批次推进方式

不要一次性把全部自然语言用例自动生成。建议按业务风险分批闭环：

1. **P0/T0：认证、会话、核心需求管理、关键状态流转**；
2. **安全：401/403、横向越权、纵向越权、输入校验**；
3. **边界：空值、长度、特殊字符、枚举值、时间边界**；
4. **一致性：重复提交、幂等、事务、异常中断后的状态**；
5. **UI：页面反馈、表单校验、关键用户路径、兼容性**；
6. **专项：AI、SSE、性能、长连接、破坏性安全验证**。

每批建议转换 5～20 条，并完成以下闭环：

```text
选取自然语言用例
→ 去泛化并确认规格
→ 编写/生成 Playwright 骨架
→ 人工审查关键断言
→ 单文件实跑
→ 验证数据清理与失败路径
→ 登记 TC ID 与 patterns 映射
→ pipeline 阶段回归
→ 根据失败根因回填用例或模式库
```

## 12. 总结

自然语言测试用例转自动化的关键不在“生成多少代码”，而在于先把业务验收规则变成明确、可验证、可重复的操作与断言。

```text
自然语言：说明测试意图
人工去泛化：明确前置、数据、操作、预期和清理
自动化代码：把明确规格变成 Playwright 操作
人工复核：确保关键断言真正验证业务规则
pipeline：统一调度、阻断失败并保留执行证据
```
