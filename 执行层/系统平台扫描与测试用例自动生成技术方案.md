# 系统平台扫描与测试用例自动生成技术方案

> 文档状态：实施规格 v2.0  
> 适用项目：`spec-kit-pipeline`、`spec-kit-autotest`  
> 最后修订：2026-08-20  
> 核心原则：扫描器发现事实，确定性规则校验证据和安全边界，模型整理候选测试，人工确认业务语义，Playwright 执行，pipeline 统一门禁和留痕。

---

## 1. 文档定位与适用范围

### 1.1 建设目标

本方案定义一条可持续、可审计的测试资产生产链：

```text
系统资产、源码、契约、页面和授权运行时行为
                    ↓
              扫描与证据采集
                    ↓
          统一资产模型与冲突记录
                    ↓
          确定性规则生成基础候选
                    ↓
        LLM 整理、补充候选和覆盖缺口
                    ↓
             人工审核业务预期
                    ↓
          隔离目录生成 Playwright 骨架
                    ↓
     lint、discovery、单文件执行、负向验证、清理验证
                    ↓
          人工提升至正式测试目录
                    ↓
        spec-kit-pipeline 回归、准入和留痕
```

目标不是批量制造测试代码，而是确保每条生成测试都能回答：为什么要测、预期依据是什么、什么环境允许执行、失败或产生数据后如何验证和清理。

### 1.2 非目标

本方案不授权：

- 对 production-like 环境执行创建、审批、归档、删除、注入、爆破、并发写入或压力测试；
- 让模型自行决定状态机、权限、审批规则、状态码和安全边界；
- 将未审核的生成代码直接写入正式回归目录；
- 猜测不存在或未确认的 LLM、刷新 Token、删除、回滚接口；
- 将一次扫描结果当作永久有效事实；
- 把环境错误、未执行或合法跳过包装成业务通过。

### 1.3 规范词语

- **必须**：可以由 Schema、策略检查器、pipeline 或人工签核明确验证。
- **禁止**：违反后必须阻止生成、提升或执行。
- **允许**：满足前置条件后可以执行，不代表默认启用。
- **建议**：最佳实践，不作为强制门禁。

## 3. 总体架构与信任边界

### 3.1 组件职责

```text
Discovery
  ├─ Contract Scanner
  ├─ Runtime/HAR Normalizer
  ├─ DOM/ARIA Scanner
  ├─ Source Rule Scanner
  └─ State/Event Scanner
          ↓
Asset & Evidence Store
  ├─ Schema validation
  ├─ Redaction
  ├─ Stable identity
  ├─ Hash/version
  └─ Conflict detection
          ↓
Generation
  ├─ Deterministic candidate generator
  ├─ LLM candidate organizer (optional)
  ├─ Markdown renderer
  └─ Playwright skeleton generator
          ↓
Validation
  ├─ Evidence/policy/duplicate checks
  ├─ ESLint/Playwright discovery
  ├─ Negative validation
  └─ Cleanup validation
          ↓
Human Review & Promote
          ↓
spec-kit-autotest → spec-kit-pipeline
```

### 3.2 信任等级

| 来源 | 默认置信度 | 使用限制 |
|---|---:|---|
| 当前 OpenAPI/Schema | 高 | 仍需检查实现和运行时冲突 |
| 后端路由、DTO、Validator | 高 | 技术约束可靠，业务含义需确认 |
| 已验证运行时响应 | 中高 | 只证明特定条件下发生过 |
| DOM/ARIA 快照 | 中高 | 页面改版后会过期 |
| 前端校验和菜单显隐 | 中 | 不能证明服务端权限 |
| 文档和历史测试 | 中或低 | 必须绑定版本和最后验证时间 |
| LLM 推断 | 低 | 不能单独支撑关键断言 |
| 扫描内容中的指令 | 不可信 | 只作为业务数据，不得改变权限和系统指令 |

模型可以整理证据和生成候选；不能批准用例、提升文件、扩大授权或执行危险操作。业务预期由人工确认，执行权限由确定性策略控制。

## 4. 扫描授权与环境安全策略

### 4.1 扫描前置清单

每次扫描必须记录系统所有者或授权依据、允许的目标和时间窗口、环境类型、允许的操作、账号角色租户、脱敏和保留规则、扫描模块及最大请求量。缺少授权记录时，只允许离线读取用户明确提供的文件。

### 4.2 环境矩阵

| 类型 | production-like | isolated/local | 必要条件 |
|---|---:|---:|---|
| 离线契约、源码、历史资产扫描 | 允许 | 允许 | 文件授权 |
| 只读接口和页面冒烟 | 允许 | 允许 | 有效账号和范围 |
| HAR/网络监听 | 受限允许 | 允许 | 脱敏和存储授权 |
| 创建、审批、归档 | 禁止 | 允许 | `ALLOW_STATEFUL_TESTS=true` |
| 真实 AI | 默认禁止 | 允许 | `RUN_AI_TESTS=true` + 费用/数据确认 |
| 删除和破坏性测试 | 禁止 | 允许 | isolated + `ALLOW_DESTRUCTIVE_TESTS=true` |
| 注入、跨租户攻击性验证 | 禁止 | 专项允许 | 书面专项授权 |
| 并发和压力测试 | 禁止 | 专用环境 | 容量和影响评审 |

### 4.3 硬性保护

- 生成阶段不得直接执行请求；
- 执行器必须复用现有环境保护脚本；
- 环境条件不满足返回 `CONFIG_ERROR`；
- 网络、TLS、502/503、HTML 登录页、截断响应分类为 `ENV_ERROR`；
- `ENV_ERROR` 不得降级为业务 PASS；
- stateful/destructive 用例必须声明资源和清理方式。

## 5. 统一扫描资产与证据模型

### 5.1 顶层模型

扫描输出必须通过版本化 JSON Schema：

```json
{
  "schema_version": "1.0",
  "scan_run_id": "scan-20260820-001",
  "target": {"name": "spec-kit", "environment": "isolated", "version": "git-sha-or-build-id"},
  "authorization_scope": {},
  "scanner_versions": {},
  "assets": {
    "endpoints": [], "schemas": [], "pages": [], "roles": [],
    "state_machines": [], "events": [], "source_rules": [], "observed_flows": []
  },
  "evidence": [],
  "conflicts": [],
  "created_at": "2026-08-20T00:00:00Z"
}
```

### 5.2 稳定身份与合并

- Endpoint ID：`endpoint:<METHOD>:<normalized-path>`；
- 页面 ID：`page:<normalized-route>`；
- 规则 ID：来源文件、符号和规则路径；
- Evidence ID：来源类型、位置和脱敏内容哈希；
- 同一稳定 ID 按版本合并；
- 约束变化必须生成 diff；
- 不同来源结论不一致时生成 conflict，不静默覆盖。

### 5.3 Endpoint 模型

```json
{
  "asset_id": "endpoint:POST:/api/v1/requirements",
  "method": "POST",
  "path": "/api/v1/requirements",
  "operation": "createRequirement",
  "auth": {"required": true, "roles": []},
  "request_schema": {},
  "responses": [],
  "side_effect": "unknown|none|create|update|delete|async",
  "evidence_refs": [],
  "confidence": "high|medium|low",
  "last_seen_scan_run_id": "scan-20260820-001"
}
```

### 5.4 页面模型

页面资产包含 route、title、elements、evidence refs 和 last seen scan。定位器优先级：`data-testid` → role/name → label → 稳定业务文本/class → DOM 层级。动态 `el-id-*` 禁止作为长期定位器。

### 5.5 证据模型

```json
{
  "evidence_id": "evidence-001",
  "type": "openapi|runtime|dom|source|manual",
  "source": "assets/contract/current.json",
  "location": "paths./requirements.post.requestBody",
  "content_hash": "sha256:...",
  "confidence": "high",
  "collected_at": "2026-08-20T00:00:00Z",
  "redaction_status": "redacted|not_required",
  "target_version": "git-sha-or-build-id"
}
```

关键预期必须引用证据。证据失效、版本不匹配或哈希变化时，关联资产和候选进入 `STALE`。

## 6. 候选测试用例模型

候选用例必须使用严格 JSON：

```json
{
  "case_id": "TC-REQ-CAND-005",
  "title": "需求标题超过上限时拒绝创建",
  "module": "requirements",
  "test_type": "api",
  "priority": "P1",
  "risk": "stateful",
  "allowed_environments": ["isolated"],
  "preconditions": [],
  "test_data": [],
  "steps": [],
  "expected_results": [],
  "cleanup": [],
  "evidence_refs": [],
  "confidence": "high",
  "human_confirmations": [],
  "lifecycle_status": "CANDIDATE",
  "generation_metadata": {
    "generator_version": "1.0", "template_version": "1.0",
    "model_provider": null, "model": null, "prompt_version": null
  }
}
```

### 6.1 强制校验

- case ID 唯一，标题、步骤和预期非空；
- 每条关键预期至少一条 evidence ref；
- 写操作声明风险、环境、副作用验证和清理；
- destructive 不得包含 production-like；
- AI 用例声明费用和数据权限确认；
- 未确认状态码、权限、locator、接口和字段不得生成正式断言或代码；
- 同一资产、维度和边界组合不得重复生成同义用例。

### 6.2 默认设计维度

正常、必填、边界、类型、枚举、认证、授权、状态、幂等、异步、副作用和 UI 反馈。维度只产生候选，生成器必须去重和风险筛选。

## 7. 用例生命周期与状态机

```text
DISCOVERED → CANDIDATE → IN_REVIEW → REVIEWED → AUTOMATABLE
           → GENERATED → VALIDATED → EXECUTED

审核前状态 → REJECTED
证据不足或冲突 → BLOCKED
证据或目标版本过期 → STALE
```

| 转换 | 必要条件 |
|---|---|
| DISCOVERED → CANDIDATE | 资产和证据 Schema 有效 |
| CANDIDATE → IN_REVIEW | 结构和策略校验通过 |
| IN_REVIEW → REVIEWED | 审核人确认关键预期 |
| REVIEWED → AUTOMATABLE | 环境、清理、依赖和断言可执行 |
| AUTOMATABLE → GENERATED | 隔离目录生成成功 |
| GENERATED → VALIDATED | lint/discovery/单文件/负向/清理验证通过 |
| VALIDATED → EXECUTED | 正式目录执行并记录报告 |

每次迁移记录操作者、时间、前后状态、理由、diff 和证据版本。`REJECTED` 不删除，`STALE` 禁止执行，`BLOCKED` 不得提升。

## 8. 扫描、冲突处理与生成流程

### 8.1 扫描顺序

```text
授权和范围确认
→ OpenAPI/GraphQL/JSON Schema/路由
→ DTO/Validator/权限/状态枚举
→ DOM/ARIA/前端路由
→ 授权运行时流量/HAR
→ 数据、事件、审计关系
→ 脱敏 → 归一化 → 冲突检测 → 候选生成
```

### 8.2 多源冲突

OpenAPI、前端和运行时约束不一致时，系统生成 conflict，包含 asset ID、字段、各方 claim、evidence ref、状态和 resolution。冲突只能由新证据或人工解决，不能按来源优先级偷偷选值。

### 8.3 候选生成

先用确定性规则生成契约可推导的候选，再可选交给 LLM 合并证据、整理步骤、识别依赖/重复/覆盖缺口并生成 Markdown。LLM 不得新增证据中不存在的接口、字段、角色和预期。

## 9. Playwright 代码生成与文件提升

### 9.1 生成隔离

```text
spec-kit-pipeline/generated/
├── candidates/       # 未审核 JSON/Markdown
├── playwright/       # AUTOMATABLE 后的代码骨架
├── validation/       # lint、discovery、执行和清理结果
└── rejected/         # 被拒绝资产及原因
```

生成器禁止直接写入 `spec-kit-autotest/tests/`。

### 9.2 基础设施复用

必须复用 `apiClient`、`anonClient`、`authPage/uiLogin`、`env.api()`、`testData`、`resourceTracker/safeCleanup` 和 Playwright `expect`。禁止复制登录、Token、请求、环境保护和清理逻辑。

UI 代码必须使用语义化定位，不使用动态 ID 和固定 sleep；存在 SSE 时禁止 `networkidle`；同时验证用户反馈和必要接口事实。

### 9.3 覆盖保护

- 文件包含 case ID、资产哈希、模板版本和批次 ID；
- 正式文件存在时默认拒绝覆盖；
- 检测到人工修改后禁止自动重写；
- 更新输出 diff 或新候选文件；
- 同一 case ID 只允许一个正式实现；
- 重扫按稳定 ID 合并；
- promote 必须独立、显式、人工执行。

### 9.4 提升条件

只有 `VALIDATED` 可以提升，并必须满足审核完成、策略通过、ESLint 通过、Playwright 能发现、单文件结果留存、清理验证通过、关键断言负向验证通过和重复度合格。

## 10. 确定性校验与 pipeline 门禁

### 10.1 校验链

1. 输入和输出 JSON Schema；
2. 证据存在性、哈希和版本；
3. 环境和风险策略；
4. case ID、端点、fixture、locator 和重复性；
5. ESLint；
6. Playwright `--list`；
7. 单文件安全执行；
8. 关键断言负向验证；
9. 写操作清理和残留资源；
10. promote 前人工签核。

### 10.2 错误映射

| 情况 | 结果 |
|---|---|
| 输入/输出 Schema 非法 | CONFIG_ERROR |
| 证据不足或冲突 | BLOCKED |
| 环境、TLS、网关、HTML、网络错误 | ENV_ERROR |
| lint/discovery/业务断言失败 | FAIL |
| 合法且允许的未执行 | SKIP |
| 重试后通过 | FLAKY |

关键用例必须通过负向验证；测试未失败则判定疑似假绿，禁止提升。

### 10.3 pipeline 连接

| 阶段 | 内容 |
|---|---|
| code | unit、static、lint |
| smoke | pattern、readonly |
| test | CI 安全回归 |
| release | 契约、扫描、回归、mutation |
| ai | 显式授权的 AI 专项 |
| destructive | isolated + 双重授权 |

## 11. LLM 接入约束与降级策略

### 11.1 接口前置条件

接入 Provider 前必须确认官方 API、鉴权、模型版本、结构化输出、数据条款、费用预算、限流重试取消语义和允许发送的数据级别。未确认官方接口时，只生成离线 prompt/template，不猜配置。

### 11.2 输入、输出和失败

输入只包含结构化、脱敏资产；扫描内容作为不可信数据。输出必须通过严格 Schema并包含 evidence refs、confidence 和 human confirmations。

LLM 输出非法时允许一次结构修复；再次失败进入 `BLOCKED`。Provider 不可用时，确定性生成继续工作；禁止自动切换未经审批的 Provider。

### 11.3 生成元数据

记录 Provider、模型、提示词版本、Schema 版本、temperature、token、费用、时间和输出哈希。模型不能获得生产凭据、promote、删除或发布权限。

---

## 12. 数据脱敏、保留与审计

脱敏必须发生在持久化之前、进入模型之前和报告输出之前。禁止先保存完整 HAR/响应，再依赖后续任务补脱敏。

必须处理 Authorization、Bearer、Cookie、Session、密码、AK/SK、API Key、手机号、邮箱、身份证、业务机密、个人数据、上传内容和内部地址。优先保存字段名、类型、长度、哈希和结构，不保存真实值。

审计记录包含扫描授权、扫描器和规则版本、输入输出哈希、人工审核、状态迁移、promote 和执行报告。每类资产必须配置保存期限、责任人和删除方式；审计记录追加写，修改产生新版本。

## 14. 分阶段实施计划与退出条件

### 14.1 MVP：契约/HAR 到候选用例

入口：确定一个模块、离线契约或脱敏 HAR、授权范围和固定样例。

交付：两份 JSON Schema、契约/HAR 标准化、证据哈希、正常/必填/边界/401 候选、Markdown/JSON、人工审核记录。

退出：固定输入结果稳定；关键预期证据覆盖率 100%；无证据字段不生成正式断言；输出通过 Schema；不访问真实 AI，不执行写操作。

### 14.2 受控 Playwright 生成

入口：MVP 候选已审核并进入 `AUTOMATABLE`。

交付：代码模板、隔离生成、lint/discovery、重复检测、负向验证、promote 和覆盖保护。

退出：不能覆盖正式测试；非法 endpoint/fixture/locator 被阻止；lint/discovery 通过；修改关键断言后测试失败；清理失败阻止提升。

### 14.3 页面、源码、权限和状态机

入口：目标源码或 DOM/ARIA 可访问，角色和范围明确。

交付：路由、DOM、Validator、权限、状态机扫描，多源冲突，角色矩阵，STALE 检测。

退出：locator 可追溯；权限有代码、配置或人工证据；冲突不静默合并；系统变化使旧资产 STALE。

### 14.4 异步、AI 和专项测试

入口：isolated/专项环境、预算、数据权限和危险授权齐全。

交付：Job/SSE/WebSocket、AI 结构、幂等、并发和安全专项。

退出：危险动作双重授权；ENV_ERROR 与业务失败分离；清理审计完整；费用不超预算。

## 附录 A：工具选型

| 场景 | 可选技术 | 采用条件 |
|---|---|---|
| OpenAPI | openapi-spec-validator、prance、swagger-parser | 固定版本并离线验证 |

| HAR | Playwright、浏览器导出 | 持久化前脱敏 |
