# Spec-Kit v2.5.0 双层测试职责与执行规则

## 1. 文档定位

本文件配套《Spec-Kit测试文档》使用，针对 `https://106.54.60.191/login` 所对应的平台核心能力，明确两层测试体系中的人工与 AI 职责、执行边界、审批责任和用例归属。

账号使用原则：`root` 仅用于管理员权限、配置可见性、审计和越权反例核验；日常创建、审批、转 SDD、任务处置和数据写入必须使用 Test/Staging 中的专用测试角色账号。生产环境只允许登录、导航和只读冒烟，不得执行创建、删除、审批、导入导出、批量评测或模型配置变更。

## 2. 双层测试模型

### 2.1 第一层：TDD 驱动的 AI 可调用测试环境

第一层回答“功能是否按契约稳定执行”。它将测试能力封装为可重复调用的 API、契约、状态机、Playwright、AI Eval、SSE 探针、性能和恢复任务，输出 JSON/JUnit/Trace/日志等机器可读证据。

**人负责定义：**

- 需求目标、范围、非范围、风险等级和验收标准；
- API、事件、AI 输出 Schema、状态机合法跃迁和权限矩阵；
- 测试数据边界、账号角色、环境白名单、配额和停止条件；
- P0/P1 红线、性能阈值、AI 黄金集人工基线和缺陷严重度；
- 哪些场景必须真模型、哪些场景只能 Mock、哪些操作禁止自动执行。

**AI/自动化负责执行：**

- 根据已批准契约生成候选用例、参数组合和边界样本；
- 执行已批准的 `contract_diff`、`api_run`、`state_machine_check`、`ui_run`、`ai_eval`、`sse_job_check`、性能和恢复任务；
- 重复运行相同测试、收集请求摘要、响应、截图、Trace、事件序列、耗时和成本；
- 对 JSON Schema、字段完整性、状态、权限返回码、幂等、事件顺序和阈值进行机器断言；
- 发现超时、5xx、契约不匹配或状态未知时停止危险写入、按策略重试或切换 Mock，并归档失败证据。

**AI/自动化不得执行：**

- 不得自行定义需求边界、风险等级、验收口径或 P0/P1 结论；
- 不得把“接口返回 200”“模型有回答”“页面显示成功”直接判为业务通过；
- 不得审批需求、批准 SDD 阶段、批准任务、接受风险、发布或回滚；
- 不得修改生产数据、生产配置、模型/Prompt/Rule/Skill 或访问未授权租户；
- 不得在写结果未知时盲目重试，不得绕过人工门禁，不得删除原始证据；
- 不得使用同一模型既生成被测产物又独立完成最终质量结论。

### 2.2 第二层：Harness + 人协同审核闭环

第二层回答“谁对范围、风险、证据和最终结论负责”。Harness 是受控编排器，不是可自由行动的超级 Agent。

**人负责定义和决策：**

- 唯一业务负责人、技术负责人、测试负责人和最终审核人；
- AI 使用的允许上下文、工具白名单、执行预算、超时和人工升级条件；
- 是否接受候选用例、是否批准阶段产物、是否批准任务执行；
- 对业务正确性、可用性、用户体验、异常影响、遗留风险作最终判断；
- 是否准出、是否回退、是否临时风险接受及风险接受期限。

**Harness/AI 负责：**

- 按已批准 DAG 调度第一层测试能力；
- 校验任务状态、制品版本、租户、环境和证据字段完整性；
- 聚合 RUN、HAR、BUG、Trace、日志、指标和截图，生成待审证据包；
- 将失败分类为 `CONTRACT_MISMATCH`、`WRITE_RESULT_UNKNOWN`、`BUDGET_EXHAUSTED`、`DATA_CONTAMINATED`、`TENANT_BREACH`、`ENV_UNAVAILABLE` 等状态；
- 触发提醒、升级和阻塞，不得将超时、缺人或缺证据自动转为通过。

**Harness/AI 不得：**

- 不得拥有 `approve`、`release`、生产写入和风险接受权限；
- 不得缺人工责任人、证据、适用制品版本或复核人时解锁下一阶段；
- 不得替人工裁决业务语义、用户体验、风险接受或上线结论；
- 不得因模型评分高、自动化通过率高或预算即将耗尽而绕过门禁；
- 不得覆盖人工意见、原始运行证据和失败日志。

## 3. 角色职责与用例归属

| 角色 | 负责定义/审核 | 负责执行的测试用例 | 不负责或无权执行 |
|---|---|---|---|
| 产品/业务负责人 | 业务目标、范围、验收标准、用户体验基线、风险接受 | 业务流程、需求内容、AI 输出可用性、UX 走查 | 不负责接口压测；不能以 AI 文本替代验收 |
| 技术负责人 | 架构约束、状态机、接口/事件契约、回滚方案 | API/契约、状态机、幂等、异常恢复、代码变更影响 | 不得单人批准自己负责的高风险变更 |
| 测试负责人 | 测试范围、风险包、红线、排期、准出规则 | 全部用例编排、独立反例、回归、证据复核 | 不得以通过率替代风险判断 |
| 接口/自动化测试 | 自动化实现、数据工厂、CI、Playwright、SSE 探针 | API、契约、状态、权限、幂等、UI 主链路、异步可靠性 | 不负责最终业务风险接受 |
| AI 质量负责人 | 黄金集、人工基线、异源复审比例、模型/Prompt 版本 | AI Schema、事实性、遗漏/误报、成本/时延、注入防护 | 不得批准 AI 自己生成的最终产物 |
| 安全测试 | 权限矩阵、攻击边界、敏感数据规则 | 越权、注入、脱敏、租户隔离、服务账号权限 | 不得批准未复测的高危漏洞 |
| 运维/DBA | 环境、配额、备份、恢复、监控和回滚条件 | 性能环境、稳定性、恢复演练、健康检查 | 不得在无审批情况下修改生产数据 |
| Harness/Agent | 工具编排、证据聚合、状态提醒、失败阻塞 | 已批准的自动化任务和只读查询 | 不得审批、发布、接受风险或生产写入 |
| 最终审核人 | 重大版本、D 级需求、准出和回滚决策 | 审核证据包与遗留风险 | 不得跳过原始证据和人工意见 |

## 4. 核心流程的责任分界

### 4.1 AI 需求助手

1. 人定义需求目标、角色、范围、非范围、验收标准、敏感信息边界和输出 Schema。
2. AI 在授权上下文内生成候选需求、澄清问题、验收标准和风险提示。
3. 自动化验证字段完整性、来源可追溯、注入防护、租户隔离、Mock/真模型差异和失败重试。
4. 业务负责人审核目标与验收标准；测试负责人审核边界、可测性和安全反例。
5. 未经人工批准只能保存草稿，不得提交、转 SDD 或进入发布结论。

### 4.2 需求分级、审批与转 SDD

1. 人定义 A/B/C/D 等级和升级理由；AI 只能提出建议。
2. 自动化验证角色权限、状态机、驳回/重提、撤回、自批限制、重复转 SDD 幂等。
3. 对 C/D 级和权限、资金、数据迁移场景，人工完成规定角色审批和最终审核。
4. 转 SDD 成功必须同时满足需求审批完成、关联唯一、证据完整和人工解锁；按钮成功不等于流程完成。

### 4.3 SDD 七阶段与 Judge

1. 人定义每阶段目标、输入输出、规则版本、阻断问题、质量门禁和解锁条件。
2. AI 生成或检查 `spec`、`constitution`、`clarify`、`plan`、`analyze`、`task`、`implement` 产物。
3. 自动化验证 Schema、来源、规则引用、过期状态、Judge JSON、证据定位、异常重试和阶段状态。
4. 人审核产物业务正确性、架构风险、数据迁移、回滚和下一阶段适用性。
5. Judge 通过、产物提交、人工批准和阶段解锁必须分别记录。

### 4.4 任务分解与实现确认

1. 人定义任务粒度、验收标准、工作区和执行白名单。
2. AI 生成任务 JSON、依赖和来源引用；自动化验证 1—12 条、字段齐全、依赖无环、任务可独立验收。
3. 人逐项批准或排除；至少一项批准且全部任务有处置，才允许实现确认。
4. Agent 只能在受控工作区执行已批准任务；实现成功仍需代码差异、测试、构建、质量门禁和交付证据。

### 4.5 SSE/异步作业

1. 人定义作业终态、超时、取消、重试和恢复规则。
2. 自动化验证 `jobId`、`tenantId`、`eventType`、`sequence`、`status`、`timestamp`、`payloadVersion`，以及断线重连、去重、重启恢复、幂等。
3. 人审核跨租户风险、用户可理解的错误提示和是否允许回退。
4. 丢事件、串租户、重复终态、重复写入和状态未知盲重试均为阻断问题。

## 5. 测试类型与自动化抽象边界

| 测试类型 | 可自动化部分 | 必须人工部分 | 首要执行角色 |
|---|---|---|---|
| 功能/API | CRUD、状态码、Schema、状态机、权限、幂等、错误码 | 业务语义、需求是否有价值、异常处置是否合理 | 接口测试 + 测试负责人 |
| AI 质量 | Schema、字段覆盖、引用、黄金集指标、成本、时延、重复性 | 事实性、业务可用性、关键样本 J0/J1、同源风险 | AI 质量 + 业务负责人 |
| 性能 | k6 并发、P95、队列、SSE 连接、资源监控 | 负载模型合理性、业务可接受性、扩容/降级决策 | 性能测试 + 运维 |
| UI | 登录、导航、关键表单、主链路、权限可见性、截图/Trace | 视觉层次、文案理解、交互顺畅、异常提示可理解性 | Playwright + UX/业务 |
| 兼容性 | 浏览器矩阵、分辨率、API 版本、事件 Schema | 关键浏览器上的视觉和业务体验确认 | 自动化 + 功能测试 |
| 用户体验 | 指标采集、页面耗时、错误率、流程完成率 | 任务完成难度、认知负担、满意度、可发现性 | 产品/UX + 功能测试 |
| 安全 | 认证、授权、越权、注入、脱敏、服务账号边界 | 风险定级、漏洞接受、修复优先级 | 安全测试 + 技术负责人 |
| 恢复/可靠性 | 故障注入、重试、重连、恢复校验、RTO/RPO 采集 | 是否满足业务连续性、是否回滚 | 运维/DBA + 测试负责人 |

## 6. 统一执行、证据和准出规则

每条用例必须填写：`用例 ID`、风险等级、功能域、测试类型、执行角色、自动化层级、前置条件、测试目的、测试步骤、预期结果、实际测试效果、结果判断、缺陷 ID、证据链接、执行日期和复核人。

判定规则：

- P0 缺陷、越权、串租户、数据损坏、重复终态、高危漏洞、恢复失败：直接阻断；不可临时豁免。
- P0 用例通过率必须 100%；发布前主链路通过率不低于 98%；失败用例必须分类，不得静默忽略。
- AI JSON/Schema 合格率必须 100%；人机一致率低于 85% 时升级复审策略。
- 普通 API P95 不高于 1 秒，列表 P95 不高于 2 秒；AI 排队不高于 60 秒、完成不高于 5 分钟，以已确认环境基线为准。
- RTO 不高于 4 小时、RPO 不高于 24 小时；SSE 丢失、串租户、重复终态为 0。
- “实际测试效果”和“本条用例测试结果判断”必须由执行人填写，AI 只能提供草稿，复核人确认后才进入准出报告。
